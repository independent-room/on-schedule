# ADR-0002: 사장님 = 네이티브 앱(Expo) / 고객 = 웹(Next.js)

상태: 채택
일자: 2026-05-03

## 컨텍스트

사용자 유형이 두 종류로 명확히 갈린다:
- **사장님**: 매일 사용, 신규 예약 푸시 알림이 핵심 가치, 고정 사용자
- **고객**: 가끔 사용(케이크 1년 1~3회), 마찰 최소가 핵심, 일회성 방문자

각 사용자에게 맞는 채널을 따로 선택해야 한다.

제약:
- 사장님 가치 1순위 = 신규 예약을 빨리 알아채는 것 → 푸시 알림 신뢰성 필수
- iOS PWA 푸시는 지원되나 신뢰성·UX 마찰(설치 안내) 있음
- 고객에게 앱 설치 강요 = 예약 포기 (베이커리 1년 1~3회 사용)

## 검토한 옵션

| 옵션 | 사장님 푸시 | 고객 마찰 | 1인 운영 | 출시 속도 |
|---|---|---|---|---|
| A. 둘 다 웹 (PWA) | 🟠 iOS 신뢰성 낮음 | 🟢 낮음 | 🟢 좋음 | 🟢 빠름 |
| B. 둘 다 네이티브 앱 | 🟢 좋음 | 🔴 설치 마찰 = 이탈 | 🔴 코드베이스 多 | 🔴 느림 |
| C. **사장님 앱 / 고객 웹** | 🟢 좋음 | 🟢 낮음 | 🟡 중간 | 🟡 중간 |
| D. 사장님 웹 / 고객 앱 | 🟠 사장님 푸시 약함 | 🔴 고객 이탈 | - | - |

## 결정

**C 채택.**
- 사장님: **Expo (React Native)** 네이티브 앱
- 고객: **Next.js** 웹 (공유 링크 기반, 회원가입 없이)

## 근거

### 1차 근거 (한국 시장·비즈니스 컨텍스트)
- **한국 시장 인식**: 한국 사장님은 "앱 = 스토어에서 받는 것"으로 인식. PWA·웹 링크는 "사이트 즐겨찾기"로 격하되어 도구로 신뢰받지 못함
- **구독료 정당성**: 월 3~5만원 SaaS 구독료는 "전용 앱"이어야 가격 인식이 성립. PWA에 월 5만원은 거부감 큼
- **바이럴 신호**: 사장님 간 입소문 단계에서 "스토어에 있어요"가 결정적 신뢰 신호 ("이 링크 들어가서 홈 화면에 추가하시면..." 대비 압도적 우위)
- **구독 결제 정합성 (ADR-0012)**: Multiplatform Service 패턴은 스토어 등재된 네이티브 앱이 전제. PWA에선 외부 결제 정책 분류 자체가 다름

### 2차 근거 (기술적)
- 사장님은 매일 쓰고 푸시 알림이 사업의 명운이 걸린 핵심 기능 → 네이티브 앱 정당화 (단 푸시 신뢰성은 부수 근거이지 1순위 아님)
- 고객에게 앱 설치 요구 = 카카오톡 DM 예약 대비 마찰이 더 커짐 = 우리 제품의 존재 이유와 모순
- 두 채널을 분리하면 각 사용자에게 최적화 가능하며, 백엔드 API를 공유해 비즈니스 로직 중복은 없음

## 결과

- 코드베이스 3개: `apps/mobile` (Expo), `apps/web` (Next.js), `apps/api` (NestJS)
- Apple Developer 계정 ($99/년), Google Play 계정 ($25 1회) 필요
- iOS 첫 심사 1~2주 버퍼 일정에 반영
- Expo Push Notifications 인프라 구축 (FCM/APNs 직접 X)
- OTA(Over-The-Air) 업데이트로 JS 변경은 재심사 우회 가능, 네이티브 모듈 변경은 재심사 필요

### 재검토 트리거
- 베타 운영 중 사장님이 "푸시 안 와도 알림톡으로 충분하다"고 빈번히 답하면 PWA 전환 검토
- iOS PWA 푸시 정책이 크게 개선되면 재검토
